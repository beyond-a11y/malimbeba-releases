Report Date October 14, 2026
Product Description Malimbe is an accessibility toolkit for developers who build software with AI coding assistants. It runs as a Model Context Protocol (MCP) server inside tools such as Claude Code, Codex, Cursor and VS Code, and provides accessibility auditing (axe-core, WCAG 2.2 A and AA), pre-release review of unhosted code, release gating, and component guidance. It includes three browser-based interfaces: a guided prompt builder, an expert prompt builder, and a component tester.
Contact Information Beyond-A11y, LLC — info@beyond-a11y.com — 833-239-6632 — beyond-a11y.com
Notes This report covers Malimbe's own user interfaces and outputs, not the accessibility of sites that Malimbe audits. Malimbe runs inside third-party host applications; the accessibility of those hosts is outside this report.
Evaluation Methods Used See "Scope and evaluation methods" below.

WCAG 2.2 A and AA include every 2.0 and 2.1 A and AA success criterion except 4.1.1 Parsing, which 2.2 removed. One set of tables below therefore covers all three versions, with the version noted per criterion.

Terms

  • Supports: The functionality of the product has at least one method that meets the criterion without known defects or meets with equivalent facilitation.
  • Partially Supports: Some functionality of the product does not meet the criterion.
  • Does Not Support: The majority of product functionality does not meet the criterion.
  • Not Applicable: The criterion is not relevant to the product.
  • Not Evaluated: The product has not been evaluated against the criterion. Used only for WCAG Level AAA.

Components in scope

Mobile screen readers are out of scope. VoiceOver on iOS and TalkBack on Android are outside this report's scope for Malimbe entirely. Desktop VoiceOver on macOS remains in scope and is reported as Not Evaluated (see the disclosure below), not as out of scope.

Evaluation methods

Testing was performed on 2026-10-12 and 2026-10-13 against the three browser-based interfaces, served locally (node ui/server.mjs, http://127.0.0.1:4173/).

  1. Automated testing. Real-browser axe-core scan (Playwright, WCAG 2.2 A and AA) via Malimbe's a11y_audit_axe tool, on all three interfaces. axe-core 4.12.1; Google Chrome 155.0.8059.40 (real, installed browser).
  2. Scripted keyboard testing. Tab-key walkthrough via Malimbe's a11y_audit_keyboard tool. Ambiguous automated flags were adjudicated by manual source inspection.
  3. Manual screen reader testing. NVDA and JAWS, all three interfaces, performed 2026-10-12 by the owner.
  4. Manual resize and reflow testing. Real-browser text resize to 210% and zoom to 400%, performed by the owner. No scripted zoom or reflow check exists in Malimbe's current tooling.

Assistive technology coverage disclosure. Screen reader testing used NVDA and JAWS. VoiceOver (desktop, macOS) is Not Evaluated: Beyond-A11y does not currently have Apple hardware in its testing toolkit. This is a standing limitation, disclosed in each remark where a Supports claim rests partly on screen reader testing.

Fix applied during testing. component-tester.html was missing a <main> landmark and had two sections of content outside any landmark (axe landmark-one-main and region, moderate). The content was wrapped in <main> and the live axe-core audit re-run, confirming 0 violations. After the fix, all three interfaces returned 0 axe-core violations (WCAG 2.2 A/AA).

Independent tool cross-check. Pa11y with the HTML_CodeSniffer engine (a different ruleset from axe-core) was run against all three interfaces on 2026-10-13. guided.html and component-tester.html: no issues. index.html: one finding — the options form had no native submit control, so pressing Enter in a text field did nothing. Fixed: the existing "Run the audit" button became a form-associated submit control, routed to the same audit action. Verified by re-running Pa11y (no issues), a functional Enter-key test in both modes, a full axe-core re-scan (0 violations) and a repeat keyboard walk (no new findings).

Audit mode tested directly. The expert view's conditionally shown Audit-mode form was opened and scanned with axe-core (WCAG 2.2 A/AA) on 2026-10-13: 0 violations.

Additional checks (2026-10-13). Reading order compared with visual position (a11y_audit_reading_order); status-message announcements (a11y_audit_status_messages); rendered-pixel contrast sampling for text over gradient backgrounds; measured border contrast of form controls; WCAG 1.4.12 text-spacing override injected into each live page; rendered size of every interactive control; scripted Tab-through reading live computed focus styles, confirmed by screenshot; and source review for focus, input, pointer, shortcut and language behavior.

Defects found and fixed before this report. Each fix was re-verified with a full axe-core re-scan:

  • Missing <main> landmark on the component tester (1.3.1)
  • No native submit control on the expert view's form (found by Pa11y)
  • Two masthead links at 4.44:1 and 4.06:1 contrast (1.4.3; commit eab8103)
  • Form-control borders at 1.38:1 contrast (1.4.11)
  • Skip link invisible while focused (2.4.7)
  • Results and mode changes not announced to screen readers (4.1.3; commit a376e8c)
  • Theme-toggle emoji (🌙/☀) read aloud as part of the button's accessible name; now hidden from screen readers on all three interfaces, so the name is exactly "Dark mode" or "Light mode" (commit 91944af)
  • No skip link on the component tester after its new header controls were added (2.4.1; commit f04f234)

Every result records the test date and method so any finding can be re-run.

Criteria Conformance Level Remarks and Explanations

1.2.5 Audio Description (Prerecorded) (2.0, 2.1, 2.2) Not Applicable No prerecorded video content exists anywhere in scope.
1.3.4 Orientation (2.1, 2.2) Supports No orientation-locking CSS anywhere (@media (orientation:...) absent).
1.3.5 Identify Input Purpose (2.1, 2.2) Not Applicable No field on any of the three interfaces collects personal/user-identity information matching the SC's defined autocomplete taxonomy (name, email, address, etc.) — every text field collects project/tool configuration (a URL to audit, a design-system reference), not user data.
1.4.3 Contrast (Minimum) (2.0, 2.1, 2.2) Supports Automated axe-core contrast checks clean on all three interfaces. Text over the gradient page background, which axe-core cannot evaluate, was checked by rendered-pixel sampling (2026-10-13): two masthead links on guided.html and index.html measured 4.44:1 and 4.06:1, below the 4.5:1 minimum. Fixed with a darker light-mode color for those two links (commit eab8103); both now measure 5.36–5.85:1. Dark mode already measured 7.0–7.7:1 and was unchanged. Re-verified with axe-core and Pa11y/HTML_CodeSniffer, both clean.
1.4.4 Resize Text (2.0, 2.1, 2.2) Supports Manual testing (2026-10-13, owner), real browser text resize to 210% (above the 200% SC threshold), across all three interfaces: presented without horizontal scroll and without loss of content or functionality.
1.4.5 Images of Text (2.0, 2.1, 2.2) Supports No image contains text used in place of real text — the only images are the brand favicon (decorative) and a user-uploaded screenshot preview (real image content, not a text substitute).
1.4.10 Reflow (2.1, 2.2) Supports Tested with real browser zoom to both 210% (above the 1.4.4 threshold) and 400% across all three browser-based interfaces. Content reflows to a single column with no loss of functionality and no two-dimensional scrolling.
1.4.11 Non-text Contrast (2.1, 2.2) Supports Real defect found and fixed (2026-10-13). Every plain-bordered text input, <select> and <textarea> on all three interfaces used a light-mode border color (#D6DCE4) measuring 1.38:1 against white, under the 3:1 minimum for UI component boundaries. Fixed by darkening the light-mode border to #7C8798 (3.64:1 against white). Dark mode's border already measured 3.12:1 and was unchanged. Verified by re-measured contrast, a full axe-core re-scan (clean on all three interfaces) and a visual check for regressions.
1.4.12 Text Spacing (2.1, 2.2) Supports Injected the standard WCAG 1.4.12 override CSS (line-height 1.5, letter-spacing 0.12em, word-spacing 0.16em, paragraph spacing 2em) into all three live pages and visually inspected full-page screenshots: no clipped, truncated, or overlapping content anywhere; no horizontal overflow (measured).
1.4.13 Content on Hover or Focus (2.1, 2.2) Not Applicable No custom hover/focus-triggered content (tooltips, popovers) exists on any of the three interfaces — searched for :hover display/visibility rules and title= attributes beyond one native iframe title; found none that create dismissible/hoverable content.
2.4.5 Multiple Ways (2.0, 2.1, 2.2) Supports All three interfaces are now mutually reachable by real, verified links, not just reasoned around for a small toolset: guided.html and index.html already cross-linked to each other; both now also link to component-tester.html ("Review this component"), which links back to whichever of the two launched it. No page is a dead end or orphaned endpoint.
2.4.6 Headings and Labels (2.0, 2.1, 2.2) Supports Clean heading-order/empty-heading results on every axe-core scan this round; every form field's label text reviewed and found descriptive (part of the 2.4.4, 1.1.1 and 3.3.2 checks).
2.4.7 Focus Visible (2.0, 2.1, 2.2) Supports Not reliably automatable by axe-core's standard ruleset (known gap — see AUDIT-COVERAGE.md). Verified by an actual visual Tab-through (2026-10-13): scripted real Tab presses across all three interfaces and read the live computed style (outline/box-shadow) at each focus stop. Every control type reached (links, buttons, radio, select, textarea) renders a visible 3px solid amber outline (#F59E0B) when focused. index.html's explicit CSS rule doesn't list textarea specifically, but nothing removes its native browser focus outline either, so it still gets a visible (if unstyled) indicator — a minor visual-consistency gap, not an accessibility defect. Defect found and fixed (2026-10-13): the "Skip to main content" link on guided.html and index.html stayed clipped to 1×1 px even while focused, so the first Tab stop showed no visible focus. Fixed with a .sr-only:focus rule that shows the link, with its focus ring, only while focused. Verified by screenshot, a full axe-core re-scan (clean) and a keyboard walk (13/13 reachable, no new findings).
2.4.11 Focus Not Obscured (Minimum) (2.2) Supports No position: sticky or position: fixed elements anywhere on any of the three pages — nothing can float over a focused control.
2.5.7 Dragging Movements (2.2) Not Applicable No drag-and-drop interaction anywhere in scope.
2.5.8 Target Size (Minimum) (2.2) Supports Measured every interactive control's real rendered size on all three pages. A few are genuinely under 24×24 (two inline text links, a few native checkboxes) — each qualifies for one of the SC's own explicit exceptions: inline text links are exempt outright; every undersized checkbox is wrapped in a <label> with substantial visible text, which is a same-function target ≥24×24 px (the "equivalent" exception), confirmed by reading the actual markup, not assumed.
3.1.2 Language of Parts (2.0, 2.1, 2.2) Not Applicable No passage anywhere is in a language other than the page's own declared lang="en" — searched for any lang= attribute beyond the root <html>; found none, meaning there's no language shift to mark in the first place.
3.2.3 Consistent Navigation (2.0, 2.1, 2.2) Supports All three pages share the masthead structure and relative order (logo/brand, context-dependent link, heading, intro, theme toggle). The component tester's back-link is a deliberate, contextual difference, not an inconsistency: guided.html and index.html are the two hub tools that always cross-link to each other and out to the component tester; the component tester needs a way back to whichever hub launched it. Same navigational role (a way to the other relevant tool), with content suited to each page's position in the flow.
3.2.4 Consistent Identification (2.0, 2.1, 2.2) Supports All three pages offer dark mode through the identical theme-toggle button: same icon, same "Dark mode"/"Light mode" label, same aria-pressed pattern, and a shared malimbeba-ui-theme storage key so the choice stays in sync across all three. Verified with an axe-core scan of the dark-mode rendered state as well as the light-mode default.
3.3.3 Error Suggestion (2.0, 2.1, 2.2) Supports The same "Enter a URL first" message doubles as the correction suggestion — it states exactly what to do.
3.3.4 Error Prevention (Legal, Financial, Data) (2.0, 2.1, 2.2) Not Applicable None of the three interfaces perform legal commitments, financial transactions, or deletion of user-controlled data.
3.3.8 Accessible Authentication (Minimum) (2.2) Not Applicable No authentication mechanism exists anywhere in these three interfaces.
4.1.3 Status Messages (2.1, 2.2) Supports Status-message check (a11y_audit_status_messages, 2026-10-13) found that results and mode changes were not announced. Fixed (commit a376e8c): the component tester's status region now announces the audit outcome ("No violations found." or "Blocked — N issues: X critical, Y serious, Z moderate.") and any errors; guided.html and index.html announce mode switches (Build/Check, Generate/Audit). The prompt and report panels, which regenerate on every keystroke, are deliberately not live regions, so screen readers are not flooded with the full text on each change. Announcement text verified on all three interfaces; axe-core re-scan clean. Confirmed with assistive technology: the owner's NVDA/JAWS re-check (2026-10-13, through commit f04f234) covered these announcements and came back clean.
